## 0. このサイトが育てるもの（Basketball IQ の定義）

### 0-1. 定義

**Basketball IQ ＝「試合中に、判断に必要な情報を見つけ、その情報をもとに選び、相手の反応に合わせて次の判断を変え続ける力」**【推測：本サイトの作業上の定義】

この定義から、教材は次の 3 つを **別々に** 評価する。

| 評価するもの | 問い | 例 |
|---|---|---|
| **見る（Situation Recognition）** | 何を見るべきか／何が起きているか | 「ドライブ中、最初に見るべきものは？」 |
| **判断（Decision Making）** | 見た情報をもとに、何を優先するか | 「コーナーのDFが寄った。どうする？」 |
| **理由（Reasoning）** | 判断の理由が、状況の手がかりに基づいているか | 「なぜ？ → コーナーのDFが寄ったから」 |

さらに、**同じ場面で相手だけ変えた問題セット** で「判断を変えられるか（適応）」を評価する。

### 0-2. 研究から言えること（根拠）と、言えないこと

| 内容 | 性質 | 出典 |
|---|---|---|
| 子どもの試合パフォーマンスの伸びは判断の伸びと関係し、判断の質はバスケットボールの知識と関係していた | 【研究】 | French & Thomas (1987) |
| 12〜13歳の選手に、映像を見ながら「なぜそう判断したか」「他の案は？」と問う11週のプログラムで、試合中の適切な判断が増え、保持された（1チーム11名の小規模研究） | 【研究】 | Gil-Arias et al. (2019) |
| 判断は、ボールを持つ時だけでなく、持たない時の動き（サポート・カバーなど）も含めて評価できる | 【研究】（評価法） | Oslin, Mitchell & Griffin (1998) GPAI |
| 画面・映像での判断トレーニングの効果は研究によって一致せず、コートへの転移は確実ではない | 【研究】 | Frontiers in Pediatrics 系統的レビュー (2026) ほか |

**研究が支えているのは「教え方」（知識と判断を、理由を問いながら教える）であり、個々のバスケの判断（例：ヘルプが来たらパス）の正しさではない。**
そのため、データ上で「教え方の根拠」と「教材の内容の根拠」を分ける（9章）。教材の内容に研究を根拠として付けることは、データチェックで禁止する。

## 1. IQ の分類を「循環する意思決定プロセス」に変える（レビュー項目1）

### 1-1. 結論：循環として扱う方が良い

v1 の 6 分類（見る・気づく・予測する・選ぶ・相手に合わせる・状況を考える）は、並列のカテゴリーだった。これだと「相手に合わせる」が独立した1つの力に見え、**1回の判断で終わる問題**しか作れない。
実際の試合では、判断の後に相手が反応し、その反応を見て次の判断をする。この「続き」を教材にするため、**循環するプロセス**に変える。

```
        ┌───────────────── 状況（前提）：時計・点差・ファウル数・チームの約束 ─────────────────┐
        │                                                                                    │
        │   ① 見る ──→ ② 気づく ──→ ③ 予測する ──→ ④ 選ぶ ──→（実行：コートで）           │
        │     ↑                                                     │                        │
        │     └──── ⑥ 次の判断 ←── ⑤ 相手の反応を見る ←────────────┘                        │
        └────────────────────────────────────────────────────────────────────────────────────┘
```

| 段階 | 選手の問い | 教材の段階（stage.kind） |
|---|---|---|
| ① 見る | 何を見るべき？ | `RECOGNITION`（mode: `WHAT_TO_LOOK`） |
| ② 気づく | 今、何が起きている？ | `RECOGNITION`（mode: `WHAT_HAPPENED`） |
| ③ 予測する | 次に何が起こる？ | `ANTICIPATION`（データ構造は用意。サンプルでは REACTION の中で扱う） |
| ④ 選ぶ | 何を優先する？ | `DECISION`（mode: `CHOICE` / `PRIORITY`） |
| （なぜ） | なぜそう選んだ？ | `REASON` |
| ⑤⑥ 相手の反応 → 次の判断 | 相手が動いた。次は？ | `REACTION` |
| 状況（前提） | 時計・点差・ファウル・約束は？ | 段階ではなく、全段階にかかる条件。コート図の `hud` と `CONTEXT_VARIATION` セットで扱う |

### 1-2. v1 との差分

| | v1 | v2 |
|---|---|---|
| 構造 | 6つの並列カテゴリー（`iq_skill` に複数タグ） | ①〜⑥が回る循環＋全体にかかる「状況」 |
| 相手に合わせる | 独立した1つの力 | ⑤相手の反応を見る → ⑥次の判断（ループの一部）。1問の中に `REACTION` 段階を入れられる |
| 状況を考える | 6つのうちの1つ | 段階ではなく「前提」。どの段階の答えも状況で変わる |
| 1問の形 | 質問1つ＋選択肢 | **段階（stages）の並び**：見る → 判断 → なぜ →（相手の反応 → 次の判断） |
| 評価 | 正解か不正解か | 見る・判断・理由・適応を **別々に** 記録 |

## 2. 「見る」と「判断」を分けて評価する（レビュー項目2）

### 2-1. v1 では可能だったか

**v1 のデータ構造では不可能だった。** v1 は 1問＝質問1つで、`key_information`（見るべき情報）は解説用の文字にすぎず、選手の答えとして記録できなかった。

### 2-2. v2 の構造

1問を **stages（段階）** の並びにする。各段階は、それぞれの選択肢・評価・フィードバックを持つ。

```jsonc
"stages": [
  { "id": "see",    "kind": "RECOGNITION", "mode": "WHAT_TO_LOOK", "show_until_step": 1,
    "prompt": "ドライブ中、最初に見るべきものは？",
    "options": [
      { "id": "s1", "text": "周りのDFの足", "cue_id": "CUE-HELP-FEET", "value": "key" },
      { "id": "s2", "text": "ゴール",       "value": "useful" },
      { "id": "s3", "text": "自分のDF",     "value": "not_now" },
      { "id": "s4", "text": "ベンチ",       "value": "irrelevant" } ] },
  { "id": "decide", "kind": "DECISION", "mode": "CHOICE", "show_until_step": 2, "prompt": "どうする？", "options": [ … ] },
  { "id": "why",    "kind": "REASON", "max_select": 2, "prompt": "なぜ？", "options": [ … ] },
  { "id": "next",   "kind": "REACTION", "show_until_step": 3, "prompt": "DFが戻った。次は？", "options": [ … ] }
]
```

- **見る問いは、判断の問いより先に出す**（判断の選択肢を見てから「見るもの」を当てることを防ぐ）。
- 見る問いの選択肢は、手がかり（`cue_id`）とつながる。だから「ヘルプDFの足」を **見られていない** のか、**見えているのに選べていない** のかを区別できる。
- 見る問いは2種類：`WHAT_TO_LOOK`（何を見るべきか＝最初の問題向け）と `WHAT_HAPPENED`（何が起きたか＝問題セットの2問目以降向け）。同じ「見る問い」を繰り返すと暗記になるため、セットの2問目以降は「何が起きたか」を問う。
- `show_until_step`：アニメーションをどこまで見せてから問うか。段階ごとに止める位置を変えられる（見る問いはドライブの途中、判断はヘルプが来た瞬間、など）。

### 2-3. 見る問いの評価（value）

| value | 意味 | 表示 |
|---|---|---|
| `key` | この判断の決め手になる情報 | 「ここを見ることが一番大事」 |
| `useful` | 役に立つが、決め手ではない | 「それも見る。でも先に…」 |
| `not_now` | 大事だが、この瞬間ではない | 「今は○○を見る時」 |
| `irrelevant` | この判断に関係ない／実際には起きていない | 「よく見よう」 |

## 3. 「なぜ？」の評価（レビュー項目3）

### 3-1. v1 の問題

v1 の理由タグは `valid: true/false` だけで、**どの選択肢の理由なのか** を持っていなかった。そのため「パス（正解）＋ 疲れていたから」と「パス（正解）＋ ヘルプDFが寄ったから」を区別できても、「理由は正しいが、選んだ判断と合っていない」は判定できなかった。

### 3-2. v2 の理由の選択肢

```jsonc
{ "id": "r1", "text": "コーナーのDFがゴールに寄った", "quality": "key", "cue_id": "CUE-HELP-FEET", "supports": ["B"] }
```

| 項目 | 意味 |
|---|---|
| `quality` | `key`＝状況の決め手となる手がかりに基づく理由／`supporting`＝正しいが決め手ではない／`misconception`＝思い込み・暗記した一般則（例：「ドライブしたら必ずパス」）／`irrelevant`＝状況と関係ない（例：「疲れていたから」） |
| `supports` | その理由が支える判断の選択肢（複数可）。**選んだ判断と理由が合っているか** を判定するために使う |
| `cue_id` | 理由が手がかりに基づく場合、その手がかり。MY IQ の「理由」の集計に使う |
| `note` | 例：「この場面では起きていない（見間違い）」。起きていないことを理由にした場合のフィードバック |

- 理由は **2つまで** 選べる（1つに絞らせると、正しい理由を2つ持っている選手が困るため）。
- 任意で **短い記述**（`free_text`）も書ける。自動採点はせず、先生が回答確認で読む。
- **データチェックで必須にすること**：最優先の判断を支える `key` の理由が1つ以上、`misconception` か `irrelevant` が1つ以上（理由の質を判定できるように）。

### 3-3. 判断と理由の組み合わせで「診断」する

| 判断 | 理由 | 診断（選手への表示） |
|---|---|---|
| 最優先を選んだ | `key`（選んだ判断を支える） | **判断も理由も的確**「見て、選べている」 |
| 最優先を選んだ | `supporting` だけ | 「判断は良い。決め手は別にある」→ key の手がかりを示す |
| 最優先を選んだ | `misconception` | **「答えは合っているが、理由が思い込み」** → 同じセットの別の問題（DF違い）を出す |
| 最優先を選んだ | `irrelevant` | **「答えは合っているが、理由が状況と関係ない」** → 見る問いの復習 |
| 最優先を選んだ | 別の選択肢を支える理由 | 「判断と理由が合っていない」 |
| 条件付き・状況次第を選んだ | その選択肢を支える理由 | 「その判断が有効になる条件を確認しよう」→ `condition` を表示 |
| 優先度の低い選択肢 | どれでも | 「この場面では優先度が低い」→ 判断ルールを表示 |

※ 点数は内部の集計にだけ使い、選手には「◎」や点数ではなく上の言葉で返す。

## 4. ◎○△× をやめ、状況に依存した表現にする（レビュー項目4）

### 4-1. 問題

v1 の ◎○△× では、選手が「◎を当てるゲーム」として解けてしまう。記号は状況から切り離され、「この選択肢はいつも◎」と覚えやすい。

### 4-2. v2 の表現

| fit | 選手への表示 | 必須項目 |
|---|---|---|
| `priority` | **この状況で優先する判断** | — |
| `conditional` | **条件付きで有効**：「○○なら有効」 | `condition`（その場面の中で、何が変われば有効になるか） |
| `situational` | **状況によっては有効**：「○○の時は有効」 | `condition`（時計・点差・相手の特徴など、場面の外の条件） |
| `low` | **この状況では優先度が低い** | — |

暗記を防ぐ仕組み：
1. **記号を使わない。** 答えた後は、全ての選択肢について「いつ有効になるか」を表示する（自分が選んだものだけでなく）。
2. **問題セットで同じ選択肢の優先を変える。** 例：SET-2V1 では「2番へパス」が問題Aでは「この状況で優先」、問題Bでは「条件付きで有効（DFがあなたに来た時は優先）」になる。データチェックで「セットの全問で最優先が同じ」ことを禁止している。
3. **選択肢の並び順は毎回シャッフル**（A・B の位置で覚えられないように）。
4. **最優先は1つ** に決める（データチェックで必須）。「何を優先するか」を学ぶため。

## 5. 「正解が一つだけ」ではない問題（レビュー項目5）

判断の段階に 2 つの形式を用意する。

| mode | 形式 | 使う場面 |
|---|---|---|
| `CHOICE` | 1つを選ぶ。最優先が1つ、他は条件付き・状況次第・優先度低 | 判断がはっきり分かれる場面（2対1でDFが来た、など） |
| `PRIORITY` | **「どの選択肢にも価値がある。この状況で何を優先する？」** と問う | 複数の判断が成立する場面（クローズアウト、時計、点差など） |

`PRIORITY` のデータチェック：条件付き・状況次第の選択肢が2つ以上、優先度の低い選択肢は1つまで（「全部に価値がある」問題になっているか）。

例（`OF-1V1-03-A`：キャッチの瞬間、DFが走ってくる）

| 選択肢 | 表示 |
|---|---|
| A シュート | 条件付きで有効：DFが遠い・遅れている時は優先 |
| **B ドライブ** | **この状況で優先**：勢いのあるDFは急に止まれない |
| C パス | 条件付きで有効：DFが間に合って構えていて、次の味方が空いていれば |
| D リセット | 状況によっては有効：ショットクロックに余裕があり、味方の位置が悪い時 |

将来の拡張（第2段階）：上位2つを順番に選ぶ「優先順位づけ」（ADVANCED 向け）。

## 7. 問題セット（レビュー項目8）

### 7-1. データ構造

```jsonc
"question_sets": [{
  "id": "SET-DRIVE-HELP",
  "kind": "DEFENSE_VARIATION",
  "scenario_id": "SCN-WING-DRIVE",
  "title": "ドライブ：DFの反応が3通り",
  "order": "fixed",                       // fixed（順番どおり）/ shuffle
  "intro": "同じドライブを3回します。あなたの動きは毎回同じ。DFの動きだけが違います。",
  "items": ["OF-DRV-01-A", "OF-DRV-01-B", "OF-DRV-01-C"],
  "closing": { "prompt": "3問で、あなたの判断を変えたのは何でしたか？", "options": [ … ] },
  "mastery_rule": "3問すべてで判断が最優先、かつ見る問いが key のとき『読めている』"
}]
```

各問題は `set_id`・`scenario_id`・`variant: { label, what_changed }` を持つ。

### 7-2. セットの種類

| kind | 何を変えるか | 例 |
|---|---|---|
| `DEFENSE_VARIATION` | OF は同じ。DF の配置・動きだけ | CASE A ヘルプしない／B ヘルプする／C ローテーションする |
| `CONTEXT_VARIATION` | コートは同じ。時計・点差・ファウル数だけ | ショットクロック 8秒／3秒 |
| `BALL_VARIATION` | ボールの位置だけ | 1パス離れ／2パス離れの守る位置 |
| `OFFENSE_VARIATION` | 相手の特徴だけ | シューター／ドライバーへのクローズアウト |
| `MIRROR` | 同じ場面を攻撃側と守備側から | 2対1を攻める／守る |
| `PROGRESSION` | 同じ場面の続き | 抜かれた → ヘルプ → ローテーション → リカバー |

### 7-3. 「同じ状況」をデータチェックで保証する

- セット内の全問で、**攻撃側の初期配置が同じ**（座標まで一致）。
- `DEFENSE_VARIATION`：DF の配置か動きが、全問で互いに違う。
- `CONTEXT_VARIATION`：コートはまったく同じで、`hud`（時計・点差）が違う。
- **判断の選択肢の文が全問で同じ**で、**最優先の選択肢が全問同じではない**（同じ答えで全問解けるセットを禁止）。
- セットの最後に **振り返りの問い**（「判断を変えたのは何だった？」）を出す。

### 7-4. セットの評価

- セット全問で最優先を選び、見る問いが key → **「読めている」**
- 一部だけ → **「1つの答えを覚えている可能性」**。MY IQ ではこちらを弱点として出す。

## 8. サイト全体構造

```
HOME（今日のセット＋続きから）
├── PLAY（考える）
│   ├── 今日の課題（先生が出したセット／問題）
│   ├── 今日のセット（毎日ちがう問題セット）
│   ├── レベル別（BEGINNER / INTERMEDIATE / ADVANCED）
│   └── 復習（「答えは合っていたが理由が違った」問題を優先）
├── MAP（知る）
│   ├── OFFENSE / DEFENSE / TRANSITION / ADVANTAGE / GAME IQ
│   ├── 手がかり図鑑（Cue：何を見るか）
│   └── ルールカード（JBA 規則の要点。判断ではなく知識）
├── MY IQ（振り返る）
│   ├── 見る力・判断力・理由（手がかり別）
│   ├── 問題セットの「読めている／覚えている」
│   └── 自分の「なぜ？」の記録
└── COACH（先生用・#/coach）
    ├── 教材一覧・確認状況（下書き→先生確認→公開）
    ├── 課題セットの作成（URL発行）
    ├── 回答確認（結果コードの読み込み）※第2段階
    └── チームの約束（TEAM_RULE）の登録 ※第2段階
```

v1 から：「今日の1問」を「今日のセット」に変更（1問だと暗記になりやすいため）。MAP に「ルールカード」を追加（タイムアウト・試合時間など、判断ではない知識の置き場）。

## 9. 根拠情報の管理（レビュー項目9）

### 9-1. 2つの層に分ける

| 層 | 何の根拠か | 使える根拠の種類 | 置き場所 |
|---|---|---|---|
| **教え方の根拠** | なぜこのサイトは「見る→判断→なぜ」と問うのか | `RESEARCH` | この設計書の 0-2 章・`sources.json` |
| **教材の内容の根拠** | なぜこの場面でこの判断なのか | `OFFICIAL_RULE`／`OFFICIAL_COACHING`／`COACHING_PRACTICE`／`TEAM_RULE` | 各問題の `evidence` |

**教材の内容に `RESEARCH` を付けることはデータチェックで禁止**（研究で「教え方」が支持されていることを、「この判断が正しい」ことの根拠と混同しないため）。将来、特定のバスケの判断そのものを調べた研究を確認できた場合だけ、この制限を見直す。

### 9-2. 問題の「どの部分」が何に支えられているか

```jsonc
"evidence": [
  { "part": "decision_rule",   "claim": "ボールから遠いほどペイント側へ寄る（寄る深さ）",
    "basis": "COACHING_PRACTICE", "source_id": "SRC-CP-GENERAL", "status": "needs_coach_review" },
  { "part": "rule_note",       "claim": "ヘルプサイドのDFはボールとマークの両方が見える位置",
    "basis": "OFFICIAL_RULE", "rule_id": "M2M-OFFBALL-VISION", "source_id": "SRC-JBA-M2M-REG",
    "locator": "3-2-1", "status": "verified_text" },
  { "part": "decide.options.C", "claim": "ヘルプサイドのDFは片足以上をヘルプサイドに残す",
    "basis": "OFFICIAL_RULE", "rule_id": "M2M-HELPSIDE-FOOT", "source_id": "SRC-JBA-M2M-REG",
    "locator": "3-2-4", "status": "verified_text" }
]
```

| 項目 | 意味 |
|---|---|
| `part` | 根拠が支える部分：`decision_rule`／`explanation`／`stage:see`／`decide.options.X`（選択肢ごと）／`rule_note` |
| `basis` | 根拠の種類。`source_id` の出典の種類と **一致しなければエラー** |
| `rule_id`・`locator` | ルールの場合は必須（`rules.json` の ID と条文番号） |
| `status` | `verified_text`（条文・本文を確認済み）／`needs_coach_review`（先生の確認待ち）／`needs_team_rule`（チームの約束の登録待ち） |

画面では、解説の各部分に小さな印を付ける：**ルール**（条文番号つき）／**指導の原則**／**チームの約束**。ルールの部分は別の枠（`rule_notes`）で表示し、コーチングの説明と混ざらないようにする。

### 10-3. 今回の確認で見つかった v1 の誤り

1. **タイムアウト**：v1 は「タイムアウトの数を知る」を選手の判断として扱っていた。タイムアウトの請求はヘッドコーチまたはファーストアシスタントコーチ（18-1）なので、選手の判断から外し、知識カードに移した。
2. **チームファウル**：v1 は「5つ目からフリースロー2本」と書いていた。条文は「クォーターごとに4個記録された後はペナルティシチュエーション。その後、ショットの動作中でない相手へのパーソナルファウルで2本」（41-1-1・41-2-1）。結果は同じだが、ボールを持っている側のファウルには適用されない（41-2-2）ため、条文どおりの表現に直した。
3. **U15 の試合時間**：v1 では解説サイトの二次情報だった。競技規則の第8条補足で確認できた（8分×4・OT3分）。

## 12. 1問の流れ（スマホ）と 5〜10 分の学習

### 12-1. 1問の画面の流れ（MVP の7ステップ）

```
① 問題を見る      コート図・アニメーションが再生され、止まる
② 何を見る？      「最初に見るべきものは？」（3〜4択）→ 一言フィードバック
③ 判断する        続きが少し再生され止まる →「どうする？」（4択、毎回シャッフル）
④ なぜ？          理由を2つまで選ぶ（＋任意で一言）
（⑤ 相手の反応）   続きが再生 →「DFが戻った。次は？」（ある問題だけ）
⑤ 解説を見る      続きを最後まで再生 → 全選択肢の「いつ有効か」→ 判断ルール → ルール枠／指導の原則
⑥ 関連する練習    練習メニュー倉庫へのリンク（例：lib-060 ドライブ＆キック 2on2）
⑦ 弱点を確認      セットの最後に MY IQ：見る力・判断力・理由のどこが弱いか
```

### 12-2. 時間の見積もり【推測：MVP で生徒に試して測る】

| 部分 | 目安 |
|---|---|
| 1問（見る・判断・なぜ・解説） | 約 1.5〜2 分 |
| 問題セット（2〜3問＋振り返り） | 約 4〜7 分 |
| 1回の学習（セット1つ＋復習1問、または セット2つ） | **約 5〜10 分** |

- 文章は1文40字以内。解説は最初は1行（判断ルール）だけ表示し、詳しくは折りたたみ。
- 途中でやめても、段階ごとに保存して続きから再開。

## 13. MY IQ（弱点の見せ方）

手がかり（Cue）ごとに、3つを分けて表示する。

| 手がかり | 見る力 | 判断力 | 理由 | 表示例 |
|---|---|---|---|---|
| ヘルプDFの足 | ○ | ○ | ○ | 「読めている」 |
| クローズアウトの勢い | ○ | △ | ○ | 「見えているが、優先を選べていない」→ 判断ルールの復習 |
| ゴールを守る味方 | △ | ○ | × | 「答えは合うが、理由が思い込み」→ 同じセットの別問題 |

- 3回以上答えた手がかりだけ判定する【推測：回数は MVP で調整】。
- 問題セットごとに「読めている（全問）／覚えている可能性（一部）」を表示。

## 14. Coach Mode・ログイン・公開（v1 から変更なし。要点のみ）

- Coach Mode：教材一覧・確認状況・課題URLの発行（MVP）。問題作成エディタ・回答の結果コード集計・チームの約束の登録は第2段階。COACH 画面は静的サイトなので本当には隠せない。秘密の情報は置かない。
- ログイン：MVP はなし（端末の localStorage のみ・名前なし）。保存部分を1か所にまとめ、将来サーバーへ差し替え可能に。中学生の個人情報を扱う前に学校の許可が必要。
- 公開：GitHub Pages（練習メニュー倉庫と同じ方式）。テスト・教材データチェックに失敗したら公開しない。
- 有料API：使わない。AI は将来も「登録済みの教材・出典・チームの約束を探す・下書きする」補助のみで、先生の確認なしに公開しない。

## 15. テスト方針（v2 で追加したデータチェック）

教材データチェック（`scripts/validate-content`、MVP の STEP 2 で実装。今回は同じ内容を一時スクリプトで実行し、15問・4セットが通ること、わざと壊した5パターンをすべて検出することを確認済み）：

| チェック | 目的 |
|---|---|
| 見る・判断・なぜ の3段階があり、この順番 | 「見る」と「判断」の分離を保証 |
| 見る問いに key が1つ以上、key の手がかりが問題の cues にある | 見る力を手がかり単位で測れる |
| 判断の最優先がちょうど1つ／条件付き・状況次第には `condition` が必須 | 「何を優先するか」を学ぶ |
| 優先問題（PRIORITY）は価値のある選択肢が2つ以上・優先度低は1つまで | 「全部に価値がある」問題になっている |
| 理由：最優先を支える key が1つ以上、思い込みか無関係が1つ以上、`supports` が実在の選択肢 | 理由の質を判定できる |
| セット：攻撃側の配置が同じ、DF（または時計）が全問で違う、選択肢の文が同じ、最優先が全問同じではない | 「同じ状況で相手だけ変わる」を保証し、暗記で解けないようにする |
| 根拠：`basis` と出典の種類が一致、ルールには条文番号、教材の内容に `RESEARCH` を付けない | 研究・ルール・指導原則・チームの約束を混同しない |
| 練習ID・戦術ID・ルールID・手がかりIDが実在 | 参照切れを防ぐ |

単体テスト（採点・診断・セットの評価・MY IQ の集計・課題URL）、Playwright（375px で1セットを最後まで解く）、ビルドは v1 と同じ。

## 16. 想定される問題点（v2 で残るもの）

1. **教材の正しさ**：内容の多くは指導原則で、先生の確認が必要。`verification` と `evidence.status` で管理し、確認前は「確認中」と表示する。
2. **画面の判断がコートに移るとは限らない**（研究結果が一致しない）。関連練習へのリンクを全問に付け、「止めて考える」練習（例：lib-250 ストップ＆ゴー・スクリメージ）とつなぐ。
3. **段階が増えて1問が長くなる**：1問 1.5〜2 分の見積もりは推測。MVP で生徒に試し、長ければ REACTION を一部の問題に絞る。
4. **見る問いの答えがヒントになる**：見る問いの後に判断を問うため、見る問いのフィードバックが判断のヒントになる。これは「見れば判断できる」ことを体験させる意図で許容する。ただし MY IQ では、見る問いを外した後に判断が正しくても「見る力」には加点しない。
